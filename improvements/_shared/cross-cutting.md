# Cross-Cutting Findings — Phase 2

Each Phase 2 review sub-agent **appends** findings here when an issue spans multiple pages / packages. Do not edit existing entries; only append.

Format per entry:

```
## YYYY-MM-DD — <Finding title> (from <package>)

**Affects:** list of packages or pages.
**Description:** 2-4 sentences. What is the issue, where does it surface, what is the consequence?
**Suggested resolution:** 1-2 sentences. One concrete approach.
**Sources:** lines or files that anchor the claim.
```

The Phase 3 synthesis (`improvements/ROADMAP.md`) sequences these refactors ahead of page-level work.

These are already documented in `gap-summary.md` "Cross-cutting refactors that should land before page-level work." Sub-agents may extend / refine them as they hit them.

5. **`AdminRole` permission expansion for CCB roles.** Per `configuration-management.md` KB the CM module needs `ConfigManager`, `SystemEngineer`, `VerificationEngineer`, `SafetyEngineer`, `CCBMember`, `Auditor` seeded as admin-role templates.
6. **Eleven audit tables → one universal provenance log.** Auditors accept the current state; engineers won't maintain it.

## 2026-05-14 — Unified baseline primitive — five patterns today (from verification)

**Affects:** `VerBaseline`, `CertBaseline`, `ParameterBaseline`, `ValidationBaseline`, `Baseline`/`BaselineItem`. ## 2026-05-14 — Universal SignatureEvent primitive — `ValidationSignOff` is the prototype (from validation)

**Affects:** Validation, Certification, Requirements (Review/Reviewer); any future module needing sign-off. Re-states seed finding #3 with a concrete starter schema. `ValidationSignOff` is the cleanest of the three current implementations — append-only via `supersededById`, no row is ever updated, revocation creates a new row. `CertSignOff` and the implicit signature inside `RequirementReview` lack the supersession chain. Migrate the three existing tables into projected rows behind read-only views during transition. The `ValidationSignOff.supersededById` chain is the right model.
**Sources:** `backend/prisma/schema.prisma:4089-4110` (ValidationSignOff schema); `backend/src/services/validation.service.ts:1199-1280` (signOff/revoke service); `improvements/validation/backend.md` §3; `improvements/validation/tickets.md` V-L1; `gap-summary.md` cross-cutting refactor #3.

## 2026-05-14 — Universal Auth `/reauth` endpoint as platform primitive (from validation)

**Affects:** Validation, Certification, Requirements review, future Tasks/CM/Documentation sign-offs. CFR 21 Part 11 §11.200(a)(1) requires two distinct identification components on each signature event with the password component re-entered for each continuous-session signing. No module reauthenticates today. Building reauth inside any single module forces every other module to duplicate.
**Suggested resolution:** New endpoint in `auth.routes.ts`: `POST /auth/reauth` accepts `{ password }`, returns `{ reauthToken, expiresAt }` valid for 60s, scoped to the requesting user. Modules requiring a signature event accept `X-Reauth-Token` in headers and validate. Auditable per call (`auth:reauth-success` / `auth:reauth-fail`). This is a prerequisite for closing gap-summary.md #1 in any module.
**Sources:** `improvements/validation/tickets.md` V-N1; `competitor-matrix.md` §3 "CFR 21 Part 11 e-signature (reauthenticated)" row; `gap-summary.md` #1.

## 2026-05-14 — Reviewer-response endpoint has cross-module authorization gap (from requirements)

## 2026-05-14 — Suspect-link propagation is non-transitive (from requirements)

**Affects:** Requirements (visible there first), but the underlying `markDownstreamLinksSuspect` is a `TraceLink` service method consumed by anywhere edits flow downstream. `traceability.service.ts:1198` does a single `updateMany` against direct links from the changed source. It does **not** walk the chain — if REQ-A → REQ-B → REQ-C and REQ-A changes, only the A→B link is flagged suspect, not the B→C link. The Jama "Live Traceability" benchmark in `competitor-matrix.md` §1 is full transitivity. The current implementation also fires once per upstream change (no batching), so a bulk-update of N requirements does N separate single-hop propagations.
**Suggested resolution:** Replace the one-hop `updateMany` with a recursive CTE that walks the link graph transitively (skeleton in `improvements/requirements/backend.md` §5.3). Add a project-scoped `suspectLinkPropagationDepth: Int` setting (default 3, max 10) to bound runaway propagation in pathological graphs. Bulk-update path collects every changed source, runs one CTE per batch.
**Sources:** `backend/src/services/traceability.service.ts:1198-1210`; `improvements/requirements/backend.md` §5.3; `competitor-matrix.md` §1 "Suspect-link propagation on upstream change".

## 2026-05-14 — `Project.strictMode` is a regulated-mode platform primitive that does not exist (from configuration-management)

**Affects:** Configuration Management, Verification, Validation, Certification, Requirements review, Safety Analysis — every module enforcing audit-grade behaviour. `kb/configuration-management.md` repeatedly cites `Project.strictMode` as the toggle that flips a project from "iterate fast" (unregulated customer, warnings only) to "lock everything, two-signer baselines, append-only audit, mandatory SafetyEngineer sign-off when `safetyImpact=true`" (regulated customer). The column does not exist on the `Project` Prisma model. Today the CM page stores `state.strictMode` in module-local reducer state with zero enforcement. Symptom: a regulated customer cannot distinguish their project posture from an unregulated customer's — the same UI affordances exist, the same one-click baseline-approve works, the same hard-delete on baselines is allowed. The validation entries on append-only signature chain (V-L1) and universal `/auth/reauth` (V-N1) both presuppose this flag but cannot enable behind it because it does not exist.
**Suggested resolution:** Prisma migration adds `Project.strictMode Boolean @default(false)`. Admin-only `PATCH /projects/:projectId/strict-mode` endpoint. Confirmation modal in the project settings page lists every constraint enabling imposes (CIs locked by baseline are immutable, ≥2 distinct approvers, release approval requires signed role set, DW transitions append-only, CR approval requires `safetyImpact` flag and SafetyEngineer sign-off when true).
